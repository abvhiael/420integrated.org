Reference / Contracts

contract addresses.

Canonical deployment records let integrators identify the correct contract for a specific network, protocol role and release, while preserving enough history to interpret older transactions safely.

required deployment record

A canonical entry should identify the network, protocol family, contract role, proxy address where applicable, implementation address where applicable, release or interface version, deployment transaction, deployment block or activation point, lifecycle status and verification source.

proxy & implementation boundaries

Upgradeable systems must distinguish the address applications call from the implementation that supplies code. Integrators should not assume the implementation address is a stable application endpoint, and historical implementation changes should remain traceable.

verification workflow

Applications should resolve addresses from the official reference and registry, confirm that the deployment belongs to the intended network, and verify the expected code or proxy relationship before sending value or granting approvals.

lifecycle

Current, superseded, deprecated and retired deployments should remain visibly distinct. Superseded records may still be required for historical decoding, but new integrations should use only deployments marked current for the relevant network and version.

cross-reference requirements

Each address record should link logically to its interface version, status definition and release record so an integrator can determine not only where a contract is deployed, but what behavior that deployment is expected to expose.

No production contract address is considered canonical here until its deployment has been qualified and verified against public network state. Missing addresses are intentional and must not be inferred.
