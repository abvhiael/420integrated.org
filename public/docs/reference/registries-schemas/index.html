Reference / Schemas

registries & schemas.

Shared registry keys and versioned record formats let independent applications resolve the same ecosystem identities, services and metadata consistently.

registry record anatomy

A canonical registry record should define its key or identifier, owner or authority, value type, schema version, lifecycle state, mutability rules, timestamp or activation context where relevant, and any relationship to another canonical registry.

normalization & uniqueness

Identity, naming and discovery schemas should state how input is normalized, which fields are case-sensitive, how uniqueness is enforced and how clients should treat aliases, missing fields or superseded values.

schema evolution

Schema changes should distinguish additive optional fields from breaking structural changes. Existing readers should be able to identify the schema version before interpreting a record, and migrations should preserve enough context to understand historical data.

ownership & authority

Reference entries should explain who may create, update, revoke or supersede a record and whether those permissions are enforced by a contract, protocol role or governance-controlled registry.

application interoperability

Applications consuming shared metadata should validate required fields, ignore unknown optional fields when safe, and avoid treating undocumented experimental fields as stable public contract.

Only stable, versioned schema definitions will be marked canonical. Experimental fields may appear during development but should not be treated as interoperable public contract until qualified.
