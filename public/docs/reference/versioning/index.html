Reference / Releases

versioning.

Version records define which binaries, contracts, interfaces, schemas and services are intended to work together and how upgrades affect integrators, users and operators.

release identity

A qualified release should identify the component or protocol family, version label, supported network, activation point, related contract deployments, interface revision and schema revision where applicable.

compatibility dimensions

Compatibility may differ across RPC behavior, contract interfaces, event layouts, registry schemas, application APIs and operator tooling. A release should state which surfaces remain compatible instead of using one broad compatibility claim.

breaking changes

Breaking changes should identify the affected interface or workflow, the last known compatible release, required migration action and any transition window. Silent reinterpretation of an existing field or event should be treated as a breaking change.

activation & migration

Where a release changes live network behavior, the reference should identify how and when that behavior becomes active: deployment, upgrade transaction, governance action, block height or another verifiable activation mechanism.

historical lookup

Superseded releases remain documented so historical transactions, events and application behavior can be interpreted using the rules active at that time. Historical availability does not mean the release is supported for new integrations.

release qualification

A version number becomes canonical only after the corresponding build or deployment has completed qualification and the supporting artifacts can be tied to an identifiable project state.

Release-specific version numbers and compatibility windows are published only after the corresponding build and deployment are qualified. Draft version labels are not public compatibility guarantees.
